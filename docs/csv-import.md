# Coordinator CSV inference and import

## Workflow

Coordinator accounts can open **CSV imports** in the application or use:

- `GET /api/imports/template` to download the current header-only template.
- `POST /api/imports/validate` with a multipart field named `file` to validate a CSV without creating records.
- `POST /api/imports` with the same multipart field to run and persist inference.

Both upload endpoints require coordinator authentication. The API accepts UTF-8 comma-separated files up to 20 MB and 5,000 data rows. Use [`processed-dataset-schema.md`](./processed-dataset-schema.md) for field provenance and meanings. The template is at `data/templates/student_upload_template.csv`.

The browser sends one `multipart/form-data` field named `file` for either operation. Do not set a multipart content type manually: the browser must add the boundary. The template is the source of truth for column names and ordering. Each file can contain many student-course rows; columns for identity, course, and every supervised feature must be present. Numeric observations may be blank when the source has no observation; they remain null and are handled by the saved model's existing preprocessing, never filled with invented values.

An enrollment number must match an active application student enrollment with the same module and presentation. Numbers are identifiers, not credentials. Unknown numbers, inactive enrollments, course mismatches, duplicate enrollment numbers, malformed rows, and invalid numeric values are reported with source row numbers. Every occurrence of a duplicate number is rejected. Valid rows in a mixed file may still be imported; invalid rows never create or modify students or enrollments. Validation returns total, valid, and invalid row counts and row-level errors before import. Uploads may not include outcome/target labels or unknown columns; `early_support_label` is training-only and forbidden. OULAD wrapper accounts are inactive and do not satisfy the active application enrollment requirement.

The accepted enrollment identifiers depend on the target database. Validate each upload against that database before importing; a CSV that is valid for one installation may not be eligible in another.

Weekly click/active-day fields are optional as a complete group. If included, all eight weeks must be supplied and the weekly clicks, active days, and active weeks must agree with the aggregate feature columns. Partial sequences are rejected, never imputed. The saved weekly LSTM is run only for a complete sequence.

## What is persisted

An accepted upload persists:

- An import audit row with the coordinator user ID, original basename, SHA-256 of the uploaded bytes, and row count.
- An aggregate feature snapshot per uploaded enrollment row.
- A supervised prediction and an individual behavioral-cluster assignment for every imported enrollment. Clustering uses the saved K-Means model and transforms the eligible uploaded students as a batch; the coordinator analytics view summarizes cluster medians and describes the observed patterns. A weekly sequence prediction is also persisted only when the complete eight-week sequence is present.

Aggregate snapshots are kept separate from `academic_records` and `engagement_records`. The API does **not** expand summary features into invented assessment scores, daily activity, attendance, outcomes, study plans, motivational messages, or interventions. The source CSV is not stored. Model outputs are generated by the configured saved model artifacts; training is never started by an upload request.

An exact byte-for-byte repeat is idempotent: the existing import and generated record IDs are returned without rerunning models. The database also enforces a unique source-file digest. There is no import-history listing endpoint yet; keep the coordinator response record IDs as the import receipt. Import does not automatically create an intervention; coordinators review model outputs and record support actions through the existing intervention workflow.

## Errors and human review

The validation endpoint returns HTTP 200 with counts and row/field errors, including for files with no valid rows. Import returns HTTP 422 when no eligible rows remain; a mixed file imports its valid rows and returns errors for skipped rows. Malformed multipart requests are rejected with HTTP 422, while oversized uploads use HTTP 413. Inference artifact failures use HTTP 503 and do not persist partial records. Database writes for a successful import are committed as one transaction.

Scores and cluster assignments are decision-support signals, not proof, diagnoses, causal explanations, or student outcomes. Coordinators review context before offering support. Cluster IDs are cohort-relative. OULAD rows are never assigned live enrollment numbers.

## Test fixture for isolated environments

`data/test_fixtures/coordinator_upload/` holds a reproducible valid/rejection upload fixture built from held-out OULAD rows, using synthetic enrollment numbers from the reserved test-only block `2403031590000`–`2403031599999`. Those numbers are not institution-issued and pass validation only after `scripts/seed_synthetic_upload_fixture.py` has explicitly seeded matching records into the separate `student_support_fixture` database on port 5433. It always refuses the application's own `student_support` database. The production validator is unchanged. See the fixture's `README.md`.
